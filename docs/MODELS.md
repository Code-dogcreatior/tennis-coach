# 模型与算法说明

## 1. 姿态模型选型（在部署机上实测）

部署机：MSI Modern 15 B12MO，i5-1235U（10 核 12 线程），16 GB 内存，**仅 Intel Iris Xe 核显（无 NVIDIA/CUDA）**，Windows 11。

基准：1080p 侧面正手片段 90 帧（`scripts/bench_pose.py`），每帧都跑检测器：

| 方案 | 每帧耗时 | FPS | 备注 |
|---|---|---|---|
| RTMPose-s + YOLOX-tiny，OpenVINO CPU | 85 ms | 11.8 | |
| RTMPose-s + YOLOX-tiny，OpenVINO GPU | 78 ms | 12.8 | 核显 FP16 下关键点平均分明显下降（0.67 对比 CPU 0.79），弃用 |
| RTMPose-m + YOLOX-m，OpenVINO GPU | 210 ms | 4.8 | 分数与 CPU 一致（0.816） |
| RTMPose-m + YOLOX-m，onnxruntime CPU | 1470 ms | 0.7 | |
| MediaPipe Pose Landmarker full，CPU | 33 ms | 30.6 | 90 帧中 5 帧没有检测到人；只有单人模型，多人场景无法指定跟踪目标 |

**选定**：RTMPose-m（body7，COCO-17 关键点）+ YOLOX-m（Human-Art），通过 rtmlib 和 OpenVINO 在核显上运行，核显不可用时自动回退 CPU。检测器**每 6 帧运行一次**，中间帧用上一帧骨架框跟踪同一人（IoU 关联），首帧选择“最大且居中”的人。实际流程中实测速度：

* 640×480（THETIS）：33.5–35.0 ms/帧
* 720p：32.8 ms/帧
* 1080p：约 85 ms/帧
* 与其他推理任务并发时为 40–55 ms/帧

选择理由：RTMPose 在快速挥拍时手腕/肘部稳定，有标准 COCO-17 定义，支持在多人画面里指定跟踪对象；MediaPipe 更快，但在多人画面中无法指定目标，个别帧丢失人体。首版只用 2D，没有使用 3D 升维模型。

姿态结果按“文件内容 SHA1 + 模型 ID + 检测间隔”缓存（`data/derived/pose_cache`），纠错后重新分析无需重新推理。

## 2. 关键点处理

1. **左右标签跳变修正**：只修正**短暂的**整肢左右互换（交换状态在 5 帧内恢复原标签才视为跳变）。最初版本按“相对上一帧”连续修正，在发球视频中造成整段标签被翻转（999 次），已改为只修正短暂跳变，并有单元测试覆盖。
2. 按真实时间戳重采样到均匀网格（支持可变帧率），≤0.25 s 的缺口线性插值，更长的缺口保留 NaN；Savitzky–Golay 平滑（约 70 ms，三阶，保留挥拍峰值）。
3. 归一化：以每帧髋部中心为原点，以整段“肩中心–髋中心”距离的中位数为尺度单位（躯干长），y 轴向上。**时间不做归一化**，节奏差异保留在时长类指标中；髋部的全局位移另行保存（用于观察重心转移）。
4. 镜头切换检测：相邻帧 HSV 直方图相关性突降视为剪辑点。速度计算和挥拍窗口都不跨越剪辑点。

## 3. 持拍手、机位、镜像

* **持拍手**：挥拍峰值前后，左右手腕的“峰值速度”和“轨迹长度”两项证据必须指向同一只手；发球则使用“抛球手先上举、持拍手随后在头顶更高处到达最高点”的模式。双手反手时持拍手不可观测，标为低置信。背面/斜后方机位下置信度减半。最后按各次挥拍的置信度加权投票。**用户填写的持拍手优先于自动估计**。
* **机位**：只统计**准备姿态和收拍后**的帧（击球前 1.6 至 0.7 秒、击球后 0.6 至 1.2 秒），不使用挥拍过程中的帧，以免把转体误判为机位变化。依据：髋宽/躯干长（髋部转动远小于肩部）、左右关节在画面中的顺序（判断面向镜头还是背向）、面部关键点可见度、鼻子相对耳朵的偏移（侧面时的朝向）。输出侧面/正面/背面/斜前/斜后，以及置信度。
* **镜像**：左手持拍者做 x→−x **并同步交换全部左右关节标签**，等价为右手持拍者（`skeleton.mirror_lr`；单元测试验证：镜像两次还原、左腕变为原右腕的镜像位置、左手挥拍规范化后与右手挥拍数值相同）。
* **不同机位不做 2D 旋转校正**。比较前先把机位归为同一类：侧面按持拍手一侧/非持拍手一侧区分；正面与斜前方可以互相比较，背面与斜后方可以互相比较。没有可比的同类机位参考时，**拒绝匹配**，提示更换参考或按参考机位重拍。

## 4. 挥拍检测、阶段切分

* 挥拍 = 手腕相对髋部速度（躯干长/秒）的显著峰值。若 2 秒内存在比它大 2.5 倍以上的峰值，就视为同一次挥拍的引拍或还原动作，不单独计数。
* 正手/反手的阶段：
  * 准备
  * 引拍：从加速坡往回找到速度谷，即引拍顶点的停顿，作为引拍终点；再越过引拍时的小速度峰，回到之前的静止点，作为引拍开始
  * 加速
  * 击球附近：**估计**，取手腕速度峰值
  * 随挥：速度回落到峰值的 20% 以下
* 发球的阶段：
  * 准备
  * 抛球/蓄力：抛球手最高点 ≈ 奖杯姿势
  * 持拍手下落：持拍手腕相对持拍肩的最低点（是手腕，不是拍头）
  * 加速
  * 击球：**估计**，取持拍手腕最高点，即手臂完全伸展；2D 下发球手腕速度峰值出现在随挥阶段，所以不用速度峰值
  * 随挥
* 没有检测球和球拍，所以所有事件都标注为“估计”。

## 5. 动作识别

1. 规则基线（可解释）：
   * 持拍手腕速度不足 → 非挥拍
   * 高点击球，且此前非持拍手上举 → 发球；高点击球但没有抛球 → 未知（如高压）
   * 加速段两手腕持续靠近 → 双反
   * 正手 vs 单反：侧面看引拍终点时持拍肩在非持拍肩之后还是之前；正面/背面看引拍终点手腕在持拍侧还是越过了身体
   * 判据接近边界 → 未知
   * **与机位无关的正/反手线索**（职业视频暴露问题后加入）：引拍终点时持拍手腕在肩线上的位置（+0.5 = 持拍肩，−0.5 = 非持拍肩）。直线上的比例在 2D 投影下保持不变，所以不依赖机位朝向的估计。
     * 阈值在 THETIS 训练组上确定：肩线位置 ≥ 0.8 且击球前非持拍手离拍 ≥ 0.7 → 正手侧（覆盖 55/68 个正手，误含 2/33 个单反）；< 0.4 → 反手侧。
     * 与机位规则冲突时，正/背面机位以机位规则为准，斜向/侧面机位以肩线线索为准。
   * **双反判定**改为“反手侧 + 击球后两手仍握在一起”，或“击球前后都握在一起”。原因是职业球员正手随挥时常用非持拍手接拍，只看击球后会把正手误判成双反（Sinner 的侧前方视频中正手全部被误判）。
2. 参考库最近邻：在击球前 1.0 s 到击球后 0.6 s 的窗口内重采样，做 DTW，按 k 个最近参考投票。与规则一致才提高置信度，不一致或距离超过阈值就判为未知。
3. **没有训练分类器**：评测结果见 REPORT.md，基线是否已经足够、训练能带来多少收益，都以那里的数据为依据。

## 6. 匹配与指标

* 参考筛选：动作类型相同 + 机位可比；持拍手已统一为右手。
* **以阶段事件为锚点逐段 DTW**（Sakoe–Chiba 带宽 35%）。特征包括：持拍腕、持拍肘、非持拍腕、双肩相对髋部的位置，肘角、膝角、躯干倾角；按段输出代价，并给出差异最大的阶段。
* 指标为 2D 投影：时长/节奏、相对峰值速度、击球附近肘角、引拍幅度/高度/身后距离、击球点前后/高度、随挥高度/路径/是否越过中线、最小膝角、肘腕速度峰值先后、髋部位移；发球另有抛球高度、奖杯膝角/肘角、下落深度、击球点高于头部、髋部上升。
  * 每个指标带机位可靠性标记：侧面专用指标在正/背面机位下停用；膝角、肘角在正/背面机位下停用。时间尺度未知时，时长和速度类指标停用。
* 与参考组对比：参考组的 \[min, max\] ∪ \[均值 ± 2σ\]，再加上各指标的最小容差；超出这个范围的**可靠**指标才生成反馈。参考组少于 3 条时，证据强度标为“低”。

## 7. 与职业动作对比（技术检查点）

目标是像教练一样指出“哪里和职业动作不一样、该怎么练”，而不只是列数值差。实现分四层：

1. **职业参考库**（`data/labels/pro_manifest.csv`，`scripts/build_pro_library.py`）：用 yt-dlp 下载职业球员训练场实拍（侧前方/侧面/背面，正常速度），作为参考视频导入，标记 `tier=pro`，只在本机分析。
   * 视频多为手持跟拍、带推拉变焦和剪辑。为此骨架归一化改为**自适应躯干尺度**：人体大小在 2 秒滑动窗口内变化超过 25% 时，按滑动中位数逐帧归一化（固定机位时与原来完全一致，有单元测试）；这种情况下髋部全局位移类指标自动停用。
   * 下载：`scripts/fetch_pro.py` 按清单下载（最高 1080p），清单的 `section` 列可只截取长视频的一段；同一视频的多个片段用 `ID#名称` 区分（如合集中的 Cazaux、Jarry 侧面发球段）。
   * 跟踪：剪辑视频切镜头后重新选人；跟踪框连续 3 次检测都对不上任何人、或当前姿态置信度很低时也重新选人（以前会把框留在原地数分钟，旧发球视频因此丢掉了 28%–67% 的时长）。
   * 挥拍标签：先用系统自己的识别结果，再按“该片段已知包含的动作”过滤（`scripts/pro_autolabel.py`）。例如双反球员被识别成单反的挥拍一律剔除，可能是切削或误判。慢动作片段（峰值速度 < 片段中位数 × 0.6）剔除。被截断的挥拍不进库。这是保守过滤，不是人工逐条审核；人工抽查结果见 REPORT。
2. **技术检查点**（`technique.py`，约 25 个）：在阶段事件（引拍终点、估计击球、随挥结束、奖杯姿势、持拍手下落）上各测一个数，例如：
   * 引拍转肩：侧面看肩线投影长度；正/背面看肩宽投影缩小比例
   * 击球前转体
   * 击球点前后/横向距离
   * 击球时手臂伸展
   * 屈膝下沉
   * 下肢蹬伸
   * 挥拍路径由低到高
   * 随挥高度、是否越过身体
   * 头部稳定
   * 发球：抛球手上举、肩部倾斜、持拍手下落、击球点高度、手臂伸展、非持拍手回收

   每个检查点声明它在哪些机位下有效：
   * 依赖水平方向的只在对应机位使用；
   * 纯垂直方向的（高度、蹬伸、下沉）在所有机位下都可用。同一机位类别的职业样本 ≥ 15 条时只用同机位的（投影仍会让垂直量随机位略有变化），不足时才合并所有机位；界面上注明用的是“同机位职业”还是“各机位职业”。
   * 在固定时间窗口内取值的检查点（如“奖杯姿势前 0.3 秒内的最低点”：屈膝、蹬伸、挥拍路径、头部稳定），不使用倍率未知的慢动作职业片段，因为窗口长度会算错。
3. **判断标准来自职业数据，不是人为设定**：
   * “正常范围”取同动作、同机位类别的职业挥拍该数值的 10%–90% 分位，再加测量容差。
   * 依赖机位的检查点只与**拍摄角度相近**的职业挥拍比较，即准备姿势髋宽投影相差 ≤ 0.07 躯干长；不足 5 条就不判断。
   * 超出范围且方向属于常见技术问题（如转肩不足、击球点偏后），才生成诊断；另一个方向只标注“超出范围但不一定是问题”。
   * 按偏离程度（以职业四分位距为单位）× 重要性排序，最多列 3 条。
4. **验证门槛**（`scripts/eval_pro_compare.py` → `checkpoint_validation.json`）：
   * 每个职业挥拍都拿“除该球员外的其他职业球员”做参考，看会不会被误报（留一球员）。
   * 误报率 ≤ 15%、样本数 ≥ 10，且在 THETIS 上没有出现“有经验球员比新手多报 20 个百分点以上”的反向现象，这样的检查点才可以进入“主要问题”；其他偏离只作为“参考性提示”展示，并写明该检查点的职业误报率。
   * 同时统计 THETIS 新手与有经验球员的触发率，作为检查点是否测到真实差别的旁证。

**展示**：
* 每条问题都附关键帧对照图：你的那一帧和最接近你的职业挥拍（阶段锚定 DTW）在同一事件的帧，裁切到人体，相关关节高亮。方向不同时职业画面自动镜像。
* 附带数值、职业中位数与范围、练习建议，可以跳到视频中对应时刻。
* 右侧播放器同步播放最接近的职业挥拍。

## 8. 反馈

只使用模板，内容来自已计算的结构化结果：观察到什么、与参考的差值和范围、证据时间段（可以点击跳转）、练习建议、证据强度。没有超出范围的可靠差异时，明确说明“找不到可靠证据”。没有使用语言模型。不做伤病判断。
